# Codex App Server v0.2 feasibility spike

**Tested:** 2026-09-25 on Windows 11, `codex-cli 0.155.0-alpha.16.3`, Node.js 24.20.0. This is a version-specific spike against an alpha CLI; App Server and several methods below are experimental. Revalidate against the exact CLI version before relying on this contract.

## Launch, authentication, and protocol

The Node harness started the installed executable directly, without a shell:

```text
codex.exe app-server --listen stdio://
```

It exchanged newline-delimited JSON-RPC over stdin/stdout, called `initialize` with `capabilities.experimentalApi: true`, then sent `initialized`. Closing stdin stopped the server cleanly with exit code 0. The initialize result did not contain a `protocolVersion` field. `codex app-server generate-json-schema --out <temporary-directory> --experimental` generated both v1 and v2 schema bundles; the installed binary reported its version in the created thread metadata.

Authentication used the existing local Codex login. The harness only checked that an account was present; it did not open, copy, or print auth files or tokens. It did not pass `OPENAI_API_KEY` or `CODEX_API_KEY` to the child.

The smallest tested child environment contained only `CODEX_HOME`, `PATH`, `SYSTEMROOT`, `TEMP`, and `TMP`. `PATH` included the Codex executable directory, Node.js, Git command tools, the bundled PowerShell runtime, and Windows system directories. That allowlist supported initialization, account/model discovery, model turns, and Windows commands on this installation; it is not a universal Windows contract.

## Verified turns and events

`model/list` advertised `gpt-6-luna` with `max` reasoning effort. A thread started on Luna completed a default turn with `effort: "max"`. The `collaborationMode` field was omitted for that default turn; the thread then reported Luna and max effort. A second turn using `collaborationMode.mode: "plan"` completed and emitted a `plan` item.

Observed lifecycle and activity methods included `thread/started`, `turn/started`, `turn/completed`, `item/started`, and `item/completed`. Item types included `userMessage`, `reasoning`, `agentMessage`, `commandExecution`, `fileChange`, `dynamicToolCall`, and `plan`. A harmless command produced start/completion events with status, exit code, and duration. A one-line file addition produced `fileChange` start/completion events. The harness did not inspect command stdout or stderr.

A supplied dynamic tool generated the server request `item/tool/call` and `dynamicToolCall` item events. The v2 schema also defines `mcpToolCall` items and `item/mcpToolCall/progress`; no MCP server was invoked in this spike, so those MCP-specific events were schema-verified but not live-verified.

## Blocking user input

The experimental request was received in Plan mode. The original live request included two questions and `isBlocking: true`; it did not include `isSecret` or `autoResolutionMs`. The client answered one question with a selected option and the other with free-form text. The server emitted `serverRequest/resolved`; no `turn/completed` had arrived before the answer, an agent-message event followed on the same turn ID, and that same turn completed. Default mode completed without emitting this request. Thus, the request path worked end-to-end in Plan mode but was not observed in default mode.

For this final pass, generated experimental schemas from installed `codex-cli 0.155.0-alpha.16.3` were compared structurally with the current upstream request and response JSON schemas; the shapes and fields matched. Exact installed shape:

- Params require `threadId`, `turnId`, `itemId`, `isBlocking`, and `questions`.
- `autoResolutionMs` is optional `uint64 | null`, default null, deprecated; its schema says to use `isBlocking` to decide whether the request blocks.
- Each question requires `id`, `header`, `question`. Optional `isOther` and `isSecret` are booleans defaulting to false. `options` may be omitted/null or an array of objects whose required fields are `label` and `description` strings.
- The response requires `{ answers: { [question_id]: { answers: string[] } } }`.

The array is meaningful, not an accidental plural: current upstream TUI code can send a selected option label plus a separate `user_note: ...` string for the same question. That is one selected option with a note, not multi-select. Its tests also show free-form answers represented in the array. Context Bridge therefore keeps the array, bounds it to one or two strings per question (each <=4 KiB, <=32 KiB total), and does not collapse it to one string. [Upstream protocol schema](https://raw.githubusercontent.com/openai/codex/main/codex-rs/app-server-protocol/schema/json/ToolRequestUserInputParams.json), [response schema](https://raw.githubusercontent.com/openai/codex/main/codex-rs/app-server-protocol/schema/json/ToolRequestUserInputResponse.json), [App Server tests](https://github.com/openai/codex/blob/main/codex-rs/app-server-test-client/src/request_user_input_tests.rs), [TUI answer construction](https://github.com/openai/codex/blob/main/codex-rs/tui/src/bottom_pane/request_user_input/mod.rs).

No `isSecret: true` request was live-triggered. Context Bridge's safe policy is to normalize `is_secret`, suppress the entire mixed or secret request, persist none of its IDs/text/options/answers/raw payload, answer with a JSON-RPC error, interrupt the turn, and expose only a generic `local_action_required` flag/error. v0.2 will not relay secret questions or answers through web ChatGPT; users must handle them outside Context Bridge, then start a new task.

The installed schema's `autoResolutionMs` is a deprecated nullable unsigned 64-bit field. Current upstream TUI comments state that it is ignored in favor of `isBlocking`; the TUI uses a fixed 60-second hidden grace period plus a 60-second visible countdown for non-blocking requests, then submits an empty answer map. This TUI behavior is not an App Server guarantee and was not reproduced by the installed protocol probe. Context Bridge will not set this field or emulate the TUI timer: it supports only `isBlocking: true`; a non-blocking request receives a protocol error and the task is interrupted/failed safely.

Sanitized wire shape (placeholder IDs; options include their required descriptions):

```json
{"jsonrpc":"2.0","id":7,"method":"item/tool/requestUserInput","params":{"threadId":"<thread>","turnId":"<turn>","itemId":"<item>","isBlocking":true,"questions":[{"id":"q1","header":"Choice","question":"Choose one","isOther":true,"isSecret":false,"options":[{"label":"BETA","description":"Use the beta path"}]},{"id":"q2","header":"Notes","question":"Any additional context?","isOther":true,"isSecret":false,"options":null}]}}
{"jsonrpc":"2.0","id":7,"result":{"answers":{"q1":{"answers":["BETA","user_note: focus on tests"]},"q2":{"answers":["user_note: include snapshots"]}}}}
{"jsonrpc":"2.0","method":"serverRequest/resolved","params":{"threadId":"<thread>","requestId":7}}
```

The example uses placeholder thread/turn/item identifiers and synthetic content; no live session IDs or request text are included here.

## Token usage and model-request counts

`thread/tokenUsage/updated` carried `tokenUsage.last`, `tokenUsage.total`, and `modelContextWindow`. Both breakdowns exposed `inputTokens`, `cachedInputTokens`, `outputTokens`, `reasoningOutputTokens`, and `totalTokens`; `cacheWriteInputTokens` was also present. The observed Luna context-window value was 258,400 tokens.

In the live run, `last` changed multiple times during a turn, while `total` increased cumulatively across turns. Treat `last` as the latest usage/context snapshot and `total` as thread-cumulative usage; neither the schema nor observed payload exposed a per-turn aggregate separate from `last`. No explicit model-request count field exists in the generated schemas or observed notifications. Token-usage notification count is not a reliable substitute for such a counter.

## Cancellation, resume, and process failure

`turn/interrupt` interrupted an active turn while its command item was running. The same thread then accepted and completed another turn. After a clean App Server stop and restart, `thread/resume` returned the same thread and it accepted another completed turn.

The harness also terminated App Server while a turn's PowerShell command was active. The command did not write its delayed marker. After restart, the same thread resumed and its last turn was `interrupted`; a subsequent turn completed. This behavior was verified locally on Windows for the tested command and timing.

## Windows sandbox and approval findings

`windowsSandbox/readiness` returned `ready`. With a standalone `command/exec` call, a `readOnly` sandbox blocked a write inside the fixture. However, `workspaceWrite` with `writableRoots` set to only the fixture still allowed a standalone command to write into a sibling directory. Therefore, `writableRoots` alone was not a strict confinement boundary for standalone `command/exec` on this installation.

For a model turn, the harness set `thread/start.runtimeWorkspaceRoots` to the fixture and used `turn/start.sandboxPolicy` with `type: "workspaceWrite"`, the fixture root, and `networkAccess: false`. A command explicitly targeting a file in the sibling directory did not create it. The thread start response did not echo `runtimeWorkspaceRoots`. The command item reported exit code 0, so the boundary check relied on the sibling file remaining absent, not on the command's exit code or output.

The final resume probe showed why temp exceptions must also be disabled. The first sibling-write attempt targeted a sibling repository under the OS temp directory and succeeded with both temp-exclusion fields omitted (their defaults are `false`). With `excludeTmpdirEnvVar: true` and `excludeSlashTmp: true`, the same resumed-thread attempt was blocked, while a write to the explicitly listed repository root still succeeded. The boundary policy for every turn must set both flags; `writableRoots` alone does not remove implicit temp access.

Generated v2 schemas distinguish two sandbox shapes: `thread/start.sandbox` is the string enum `"workspace-write"`, while `turn/start.sandboxPolicy` is the structured `{ type: "workspaceWrite", writableRoots, networkAccess, excludeTmpdirEnvVar, excludeSlashTmp }` object. Passing the structured object to `thread/start.sandbox` returned JSON-RPC `-32600` (`invalid value: map, expected map with a single key`); using the documented string enum succeeded.

## Resume root boundary

Installed `ThreadResumeParams` accepts optional `runtimeWorkspaceRoots` and `cwd`; `ThreadResumeResponse` contains `runtimeWorkspaceRoots` and `cwd`. The resume root list is a replacement, not an immutable historical restriction. A throwaway thread was created in repo A, completed a turn, App Server exited cleanly with code 0, and a fresh process resumed the same thread with repo A reasserted. The response returned exactly repo A as its effective root and cwd. The next turn explicitly reasserted repo A and used workspace-write with only repo A writable, network disabled, and both temp exclusions enabled. The model attempted to create a file in sibling repo B; the file remained absent and a command-execution item was observed.

The response proves the effective resumed configuration only; it does not attest to the thread's historical origin. Context Bridge must retain a private local binding from thread ID to project registration/root fingerprint, refuse when that binding is missing or mismatched, reassert the expected root on resume and turn start, and verify the response's exact root list and cwd before starting work. Do not rely on the App Server response alone as project identity.

## Concurrent different-project turns

Using one App Server process, the resumed repo-A thread started a long-running command turn. While that command was active, a new repo-B thread and turn started and its command item began before turn A completed. The client correlated item/turn notifications by distinct thread and turn IDs. It then interrupted A: A completed as `interrupted`, while B completed normally. Both throwaway marker files were written inside their respective roots, and neither marker appeared in the other repository. No command stdout/stderr was read. This verifies two different-project turns can overlap and cancel independently on this Windows installation; it does not cover same-project concurrency or establish a four-turn limit.

## Cross-process lock research and prototype

Candidate design: keep one stable lock file per canonical-root fingerprint in the private Context Bridge config directory and hold an exclusive whole-file kernel lock for the project's active turn. Use `flock` on Linux/macOS and `LockFileEx` on Windows. The kernel lock, not PID or elapsed time, determines ownership; process death releases it. Do not unlink/replace the file while any Context Bridge process may be running. Add an in-process mutex as a second layer. A hash-derived filename avoids placing project roots in lock metadata or MCP output.

`@lickle/lock@0.0.1` was prototyped outside the repository under Node 24 on Windows. One process acquired the lock, two independent contenders were denied, the holder was forcibly terminated, and a fresh process then acquired the still-existing lock file. No PID metadata or shell locking command was used. Its native implementation uses `flock` on Unix and `LockFileEx` on Windows; its published targets are Windows x64, Linux x64 GNU, macOS x64, and macOS arm64. It does not publish Linux ARM64 or musl bindings. The package is new (`0.0.1`, small repository/maintainer footprint); upstream CI defines Node 20/22 tests across Windows/macOS/Linux targets and Node 24 builds, but Context Bridge has not run its own multiprocess test on Linux/macOS or Node 20. Therefore the kernel-lock mechanism is the leading candidate, but the production package remains unresolved pending native cross-platform tests, a dependency maintenance review, and exact target coverage.

`proper-lockfile` was excluded because stale lock takeover depends on elapsed time. `os-lock` is an older native option with no current cross-platform prebuilt evidence. `fs-ext-extra-prebuilt` exposes a broader NAN-based filesystem API and is also a very small-maintainer fork despite wider downloads; it is not selected. If the candidate dependency does not pass Context Bridge's full matrix, keep locking unresolved rather than substituting PID-only or age-only ownership.

Thread/turn requests accepted `approvalPolicy: "never"` and `"on-request"`. No approval request was observed for an ordinary command or the denied sibling write; this spike does not establish when the server escalates a command for approval. With `networkAccess: false`, a `curl.exe` request to an external HTTPS host failed with exit code 7; curl was present. Stdout/stderr were not read and no network-enabled control request was made, so the observed result confirms connection failure under the requested policy but does not identify the OS-level denial reason.

## Adapter recommendation

App Server is suitable as the local orchestration protocol for an experimental v0.2 adapter, with safeguards:

1. Spawn the executable directly over stdio, use an explicit environment allowlist, negotiate `experimentalApi`, and version-gate against the installed CLI/schema.
2. Start new threads with the canonical project root in `runtimeWorkspaceRoots`; set an explicit `workspaceWrite` policy with only that root writable, network disabled, and both temp exclusions enabled on every turn. On resume, validate the private thread/root binding, reassert the root, and verify effective roots/cwd in the response before starting a turn.
3. Do not expose standalone `command/exec` as a project-confined generic tool based only on `writableRoots`; its sibling-write result requires a separate containment boundary or exclusion from the adapter.
4. Handle `item/tool/requestUserInput` only when `isBlocking: true`; preserve the upstream answer string array with strict bounds, suppress any `isSecret` request from ChatGPT, and do not emulate deprecated `autoResolutionMs`. It was observed in Plan mode but not in default mode; that does not establish that default turns cannot emit it. The method is experimental.
5. Record item/lifecycle and token-usage notifications, but do not claim exact model-request counts from token notifications.

**Suitability:** conditional yes for controlled local thread/turn orchestration with the safeguards above; no as the sole security boundary for standalone command execution. Two different-project turns can overlap on the tested Windows build. The main caveats are experimental protocol stability, user input observed in Plan but unverified in default mode, temp-directory exclusions required for the Windows boundary probe, Linux/macOS live validation, and an unresolved production lock dependency.
