## 1. Goal and scope

v0.2 adds explicitly authorized local Codex orchestration to v0.1's read-only inspection server. An MCP client starts or continues a bounded task, polls it, relays a blocking user question, answers on the same active turn, cancels work, then reviews actual changes through existing filtered Git tools.

In scope: Codex App Server over stdio JSON-RPC; local per-project opt-in and profile policy; exactly six new task tools; persistence/recovery; Plan mode; sanitized usage/activity telemetry; one writer per project.

Out of scope: generic shell, standalone App Server command/exec, arbitrary Git/RPC/configuration, automatic stage/commit/push, approval forwarding, network-enabled tasks, multiple project writers, worktree isolation, permanent daemon, hosted service, other providers, analytics dashboard, exact cost/quota inference, npm publication.

App Server is experimental/version-sensitive. Compatibility checks must fail closed. Keep package private and preserve the existing nine MCP contracts and v0.1 security behavior.

## 2. Architecture

Use one lazily started App Server process per Context Bridge process and one process-wide TaskManager/AgentAdapter shared across stdio and HTTP handlers. Do not create a manager per HTTP request. Allow at most four active turns across different projects; a fifth returns agent_capacity. No unbounded queue.

Suggested modules:

    src/agents/adapter.ts             # minimal provider-neutral interface
    src/agents/policy.ts              # local authorization
    src/agents/profiles.ts            # profile validation/resolution
    src/agents/codex/app-server.ts    # child lifecycle and JSON-RPC framing
    src/agents/codex/protocol.ts      # bounded types and capability gate
    src/agents/codex/adapter.ts       # Codex method/event mapping
    src/tasks/types.ts                # public/persisted types
    src/tasks/store.ts                # versioned local persistence
    src/tasks/manager.ts              # lifecycle and idempotency
    src/tasks/runtime.ts              # exclusive task-runtime ownership/recovery
    src/tasks/signals.ts              # in-process long-poll notifications
    src/mcp/tools/tasks.ts            # six task schemas/handlers

AgentAdapter supports only model/capability discovery, thread start/resume, turn start/interrupt, supported blocking-request answer, normalized event subscription, and close. No command execution, arbitrary RPC, or arbitrary config method. Implement only Codex. Keep process management out of mcp/server.ts.

On Context Bridge shutdown, stop accepting work, interrupt active turns, persist outcomes, close App Server stdin, wait a bounded interval, then terminate only its child. App Server stdout is protocol-only; stderr is bounded local diagnostics, never raw MCP output.

## 3. Trust and authorization

Project registration continues to grant read-only inspection only. Execution is disabled for all existing and new projects until explicitly enabled by local CLI. Add:

    ctxbridge agent enable|disable|status <project-id>
    ctxbridge agent profile list
    ctxbridge agent profile add <name> --model <model-id> --effort <effort>
    ctxbridge agent profile remove <name>
    ctxbridge agent profile default <name>
    ctxbridge agent policy show <project-id>
    ctxbridge agent policy set <project-id> --allow-profile <name>... [--default-profile <name>]

Enable requires an interactive TTY confirmation; no unattended bypass in v0.2. Warn that Codex gets direct workspace access, can read files hidden by Context Bridge's denylist, and can modify project files. Only an accessible Git repository may be enabled. Disable blocks new work; first cancel or finish active tasks.

First enable allows only the global default profile. Other profiles require explicit local policy; project default must be allowed. MCP clients select only configured allowed profile names. Project removal invalidates authorization and fails while active/waiting work exists. Re-registration does not restore authorization or old MCP task access.

Before every turn, reload registry, canonicalize the root, verify task/registration identity, confirm policy/profile, recheck Git, and acquire writer lock. New threads set `runtimeWorkspaceRoots` to exactly the canonical root and `sandbox` to `workspace-write`. Every turn explicitly sets `workspaceWrite`, `writableRoots` to only that root, `networkAccess: false`, `excludeTmpdirEnvVar: true`, `excludeSlashTmp: true`, and `approvalPolicy: never`, using fields validated against the installed schema. The temp exclusions are required: on Windows, a sibling write under the OS temp directory succeeded when both temp-exclusion fields were omitted (their defaults are `false`); it was denied after both exclusions were enabled while the explicitly listed project root remained writable. No extra writable paths. Fail closed if protocol cannot express these values.

Persist the upstream Codex thread ID in the private local task record so a future runtime can continue that same thread after restart. Treat it as private internal metadata: never expose it in MCP output, CLI output, errors, events, logs, or filenames. Never persist upstream JSON-RPC request IDs; future pending-request correlation is in-memory only. A task record binds history only to project ID, display name, registration UUID, and registration timestamp; it never stores a raw/canonical project root or root fingerprint. At `task_start`/`task_continue` time, obtain the current canonical root from the registry and require current enabled authorization whose private root fingerprint matches the registration. `thread/resume` accepts `runtimeWorkspaceRoots` as a replacement and returns effective `runtimeWorkspaceRoots` and `cwd`; these fields verify the effective resumed configuration, not the thread's historical origin. On every resume, require the stored registration binding to match, explicitly reassert the single expected canonical root, then verify the response contains exactly that root and matching `cwd`. Also reassert the root and full sandbox policy on `turn/start`. If the stored binding is absent/mismatched, the response omits or changes either root value, or any required policy cannot be reasserted, `task_continue` refuses to run.

All project work uses model thread/turn methods. Never call or expose standalone command/exec. Internal commandExecution events are model activity, not a Context Bridge execution API.

Enforcement depends on Codex runtime/OS sandbox and is stronger permission than v0.1 read-only filtering. Standalone command/exec can escape `writableRoots`, so it is prohibited. A Windows resume-turn sibling-write probe was blocked when both `excludeTmpdirEnvVar` and `excludeSlashTmp` were true; the same probe succeeded when both temp exclusions were left at their defaults. This is version-specific, not formal OS proof. Context Bridge filtering does not mediate Codex workspace reads/writes. Network is always false; one failed request is not proof of universal isolation. Explain limits before enablement and in SECURITY.md.

Use the user's existing Codex authentication. Never read/copy/log/return credentials. MCP cannot set model ID, Codex config, sandbox, approval, network, cwd, environment, executable, or flags.

## 4. Local configuration and profiles

Keep the `projects.json` v1 envelope and existing fields. M3A adds an optional `registrationId` UUID to each project entry; pre-M3A v1 records without it remain readable. Existing agent authorization without a matching registration ID is stale and requires an explicit local TTY re-enable, which first persists an ID for that registration. In the per-user config directory store `agent-policy.json`, `tasks/<uuid>.json`, one stable `agent-locks/config-mutation.lock`, stable `agent-locks/project-<sha256-canonical-root>.lock` files, and `agent-locks/task-runtime.lock`. Lock files contain no root/PID owner record and are never unlinked or replaced while Context Bridge may be running. Task JSON files are the source of truth; M3B uses only in-memory task/idempotency indexes. Use `schema_version`, restrictive permissions where supported, temporary sibling + flush + replace, temp cleanup, and tested Windows replacement. Corrupt/future schemas fail closed; never reset to empty.

Logical agent-policy.json:

    {
      "schema_version": 1,
      "default_profile": "luna-max",
      "profiles": {
        "luna-max": { "model_id": "gpt-6-luna", "reasoning_effort": "max" }
      },
      "projects": {
        "project-id": {
          "registration_added_at": "ISO timestamp",
          "registration_id": "UUID from projects.json",
          "root_fingerprint": "private SHA-256",
          "enabled": true,
          "allowed_profiles": ["luna-max"],
          "default_profile": "luna-max"
        }
      }
    }

luna-max is the initial default, gpt-6-luna/max. sol-high (gpt-6-sol/high) is an optional locally added example, never silent fallback. Profile names are stable Context Bridge IDs; model IDs/effort remain local and MCP cannot provide them. Names are lowercase kebab-case, 1–64 chars. Validate profiles at add and before use against model/list. Unsupported model/effort gives a clear error, no substitution.

Start profile precedence: explicit allowed profile, project default, global default. Continue inherits task profile unless explicitly overridden by an allowed profile. A referenced profile cannot be removed. Project policy updates fail atomically if invalid.

Agent policies bind project ID, registration ID, registration timestamp, and private canonical-root fingerprint. Task history stores project ID, display name, registration ID, and registration timestamp only; it does not duplicate the root or fingerprint. Records may remain locally after project removal, but future task_get/tasks_list require a current matching registration; continuation also requires enabled policy. Never expose registration ID, root, or fingerprint.

## 5. Persistent task/turn records

Task record: strict `schema_version: 1`, UUID task_id, project ID/display name/registration identity, state/timestamps, detected Codex version, current profile, turn_count, nullable private `private_thread_id`, turns, hashed idempotency records, bounded final response, safe error, usage summary, and a bounded event timeline. Top-level usage summary holds cumulative `thread_total`, latest `latest_last`, the most recently known `model_context_window`, `delta_quality`, and `model_request_count: null`. New records initialize token counters and context-window values to null with quality `unavailable`; M3B originally collected no telemetry, and M6 fills these existing fields. The thread ID is persisted solely for future same-thread continuation and remains private internal metadata. Do not persist raw request IDs, JSON-RPC IDs, canonical roots, or root fingerprints.

Turn record: turn_number, mode, profile, internal model ID for local analytics, prompt preview/hash, state/timestamps, user-input wait, Git baseline, cumulative usage `start_total`/`end_total`, `latest_last`, derived `turn_delta`, `model_context_window`, `delta_quality`, `model_request_count: null`, a fixed per-turn `activity_summary`, and bounded final assistant response/truncation. Each token breakdown contains exactly `input_tokens`, `cached_input_tokens`, `cache_write_input_tokens`, `output_tokens`, `reasoning_output_tokens`, and `total_tokens`, each a nonnegative integer or null. Context-window size is a separate positive integer or null. M3B initialized snapshots as null and did not compute deltas; M6 records totals/deltas and count/duration aggregates. Earlier schema-v1 turns without `activity_summary` load with an all-zero fixed summary and gain it on the next record write.

Store prompt preview <=512 UTF-8 bytes and SHA-256 full prompt hash, not full prompt. Final response <=64 KiB; never persist reasoning/tool output as final response. Codex owns conversation history.

Never persist/return project roots or root fingerprints, upstream JSON-RPC IDs, credentials/environment, raw protocol, command text/stdout/stderr, reasoning, file content, MCP arguments/results, secrets, or event paths. The persisted upstream thread ID is the sole exception: it is private local metadata, never returned or logged, and never used as a filename. Final assistant text may contain workspace material Codex read directly and is not filtered like file_read/git_diff; state this in the enable warning.

## 6. State machine and locks

States: queued, running, waiting_for_input, completed, failed, cancelled, interrupted. queued/running/waiting are active; waiting holds the writer lock.

    queued -> running | failed | cancelled | interrupted
    running -> waiting_for_input | completed | failed | cancelled | interrupted
    waiting_for_input -> running | failed | cancelled | interrupted
    completed | failed | cancelled | interrupted -> queued (by appending a new turn; the old turn stays terminal)

Terminal task with thread ID may continue, including cancelled/interrupted; active task may not. No thread means not resumable. Continue adds a turn to the same task/thread.

Lock each project before a turn; retain through input wait until terminal state is durable. Contention returns project_busy and active_task_id. Different projects run concurrently up to four-turn cap; same-project concurrency is prohibited. Locks must protect multiple Context Bridge processes, not only in-process calls.

M3A selects optional dependency `fs-ext-extra-prebuilt@2.2.14`, loaded only when a configuration or project lock is requested. Its published prebuilds cover Windows, Linux, and macOS on x64 and ARM64, with Node 20–25 binaries; Linux musl and other missing bindings are unsupported and fail closed. On Unix the package's exclusive `flock` API uses the kernel file lock; on Windows that API uses `LockFileEx`. The package's install build script is denied so an unsupported target does not block installation or ordinary read-only startup. The dependency's upstream includes automated prebuild refreshes; the earlier `@lickle/lock@0.0.1` candidate was rejected because its published binding set omits Linux ARM64 and it has substantially less maintenance activity.

Configuration mutations acquire the one global lock with nonblocking attempts, an increasing delay, and a 5-second default deadline. Expiry returns sanitized `config_busy`. Registry add/remove/initialization and every agent-policy read-modify-write use this same lock; the read for each mutation happens only after acquisition. Project writer acquisition is nonblocking and uses SHA-256 of the normalized canonical root, never the raw path. A synchronous process-local reservation keyed by the exact stable lock path prevents same-process reacquisition; the OS lock remains the cross-process authority. The OS releases ownership when the holder process dies. Lock files are stable empty files: release unlocks and closes the file handle, and no code unlinks or replaces the file. An unavailable binding or ambiguous native result fails closed; read-only MCP calls do not load the binding. GitHub Actions run 36209781951 passed all six supported jobs: Windows, Ubuntu, and macOS with Node 20 and 24. Both same-process reservation tests and real multiprocess native-lock tests passed in every job. Linux musl is unsupported. CI also reports the Actions Node 20 runtime deprecation (actions run on Node 24) and the upcoming `ubuntu-latest` migration to Ubuntu 26; these are infrastructure notices, not product blockers.

M3B adds a second, process-wide task-runtime ownership lock at `agent-locks/task-runtime.lock`. Starting the internal task runtime is nonblocking and exclusive across processes; contention returns sanitized `agent_runtime_busy`. The owner holds the OS lock for the complete runtime lifetime. Clean close wakes waiters, drains in-flight serialized mutations, then releases ownership; ambiguous release fails closed. No PID or mtime-based ownership is used. The lock is not acquired by ordinary Context Bridge startup or read-only MCP calls, so another process may continue to serve v0.1 registry/files/Git tools while it cannot own task persistence. Process death releases the lock in the OS; the next owner performs durable recovery before exposing its internal manager.

Task-store bounds are explicit: at most 1,000 task files and 64 MiB total serialized data are scanned at startup; one task file is at most 6 MiB; each task has at most 64 turns, 128 idempotency entries, and 1,000 detailed events. Prompt previews are at most 512 UTF-8 bytes and final responses at most 64 KiB. Unknown files in the task directory fail closed. Stale temp files are not treated as task records or deleted automatically; repair is local/manual. Limits do not trigger silent history deletion.

## 7. Six MCP contracts

Inputs are strict Zod objects rejecting unknown fields. IDs/configuration are Context Bridge-owned. Success structuredContent and JSON text follow current convention. Errors are isError with sanitized structured error. Existing nine names/contracts/annotations stay unchanged.

Bounds: project_id existing kebab-case 1–64; task_id UUID; prompt nonempty UTF-8 <=32 KiB/no NUL; profile 1–64 kebab-case; mode default|plan defaulting to default; optional request_id 1–128 printable ASCII, installation-scoped; event page 1–100 default 50; list 1–100 default 20; `task_get.wait_ms` 0–30,000 default 0; at most two upstream answer strings per question, each <=4 KiB and <=32 KiB total per request; final response <=64 KiB; timeline <=1,000 events/task. Enforce UTF-8 byte limits explicitly.

task_start/task_continue return TaskAcceptedOutput; task_get returns TaskGetOutput; tasks_list returns TasksListOutput; task_answer returns TaskAnswerOutput; task_cancel returns TaskCancelOutput. The schemas intentionally omit upstream thread/request IDs and raw model IDs.

When include_final_response is false, return final_response null and final_response_included false; otherwise set the flag true even when no final response exists. Top-level task usage summarizes the latest thread-cumulative snapshot; turn usage contains that turn's own delta and quality.

### task_start

Require registered Git project, enabled policy, allowed profile, free lock and valid idempotency. Persist intent, capture baseline, start new thread/turn. Return after App Server accepts initiation, never after completion. On post-allocation failure persist terminal state.

Success: task_id, project_id, display_name, state, turn_number, profile, mode, created_at, updated_at. No prompt/root/model/thread ID.

### task_get

Return identity/project, state, profile, turn_count, current_turn or null, latest_turn, bounded sanitized events, pending_input or null, `local_action_required`, optionally bounded final_response, usage, safe error or null, timestamps, truncation metadata. Events have seq/time/turn/category/kind/lifecycle/status/optional duration, no paths/content. Pagination: next_after_seq, has_more, events_truncated_before_seq when needed.

`wait_ms` defaults to zero and is bounded to 30,000. Read a durable snapshot first and return immediately when `event_seq > after_seq`, the task is already waiting for input, or the task is terminal. Otherwise, subscribe to a per-task state/event signal and race it against one timeout; writers signal only after the state/event update is durable. Recheck after subscribing to close the lost-wakeup race, then reread and return the normal snapshot on an event, state change, pending input, terminal transition, timeout, or MCP cancellation. Do not hold task/project locks while awaiting; remove the listener/timer on every exit and do not poll in a loop. The v0.2 single-owner runtime delivers these signals in-process.

Long polling is useful only while the MCP caller's web-chat turn remains active. An ordinary MCP server cannot guarantee it will spontaneously push a new question into an idle ChatGPT conversation after that turn has ended. Bounded `task_get` long polling is the v0.2 mechanism; MCP elicitation remains optional future work.

Each turn's compact Git baseline has branch, HEAD or null (unborn), staged/modified/deleted/untracked counts and truncated. Use git_status/git_diff for actual path lists and current review.

### tasks_list

Recent summaries only: task_id, project_id, display_name, state, profile, turn_count, created/updated/latest-turn timestamps, pending_input boolean, truncated. Sort updated descending then task_id. No events, previews or final responses.

### task_continue

Require terminal task with thread, matching current project identity and enabled policy. Use explicit allowed override or inherit profile. Verify the stored thread/project/root binding, resume the same thread with the expected root reasserted, verify returned effective `runtimeWorkspaceRoots` and `cwd`, then set the same root and complete sandbox policy on the turn. Refuse continuation on any missing or mismatched proof. Capture baseline and start the new turn only after these checks. Return on initiation. Reject active task/project writer. A task marked `local_action_required` is not continuable; after handling it outside Context Bridge, the user starts a new task.

### task_answer

Require waiting_for_input and current unresolved pending_input_id. Answers contain every received question ID exactly once and no extras. Preserve IDs as opaque strings. Preserve the upstream `answers: string[]` shape: accept 1–2 bounded strings per question (maximum 4 KiB each and 32 KiB total per request). A single selected option must exactly match its label. A free-form answer is allowed only when no non-empty options were supplied or `isOther` is true. Two strings represent one selected option plus an optional free-form note; this is not multi-select. Preserve their order and contents.

Forward via private upstream request ID; return task_id, pending_input_id, turn_number, resulting state normally running. Never create a new turn. Stale, repeated, incomplete, duplicate or unknown answers fail without forwarding.

### task_cancel

Queued/unaccepted work becomes cancelled. Running/waiting calls turn/interrupt once and waits for terminal event. Idempotent. Completed/failed/cancelled/interrupted returns unchanged. Process loss before confirmation means interrupted. Cancellation can leave partial edits; never rollback.

### Output schemas/errors

Define and validate Zod response schemas:

- Start/continue: UUID task_id, project_id, display_name <=256, state, turn_number >=1, profile, mode, ISO timestamps.
- Event: positive seq/turn, timestamp, category task/turn/item/user_input/usage/system, bounded kind or other, lifecycle/status enum, optional nonnegative duration.
- Pending question: question ID <=256, header <=256, question <=4096, <=20 options with labels <=512 and descriptions <=2048, is_other boolean; <=10 questions. Reject oversized/malformed input, never truncate meaning.
- Usage counters are nonnegative integers or null; model-request count null/unavailable; truncation flags explicit.

Error fields: code, safe message, retryable, optional task_id/active_task_id. Codes include project_not_found, project_not_git, agent_disabled, profile_not_found, profile_not_allowed, request_id_conflict, project_busy, agent_capacity, agent_instance_busy, codex_runtime_unavailable, codex_unauthenticated, app_server_incompatible, model_unavailable, effort_unsupported, task_not_found, task_not_resumable, task_active, pending_input_not_found, pending_input_stale, invalid_answers, secret_input_requires_local_action, task_store_error, app_server_error. ## 11. Telemetry

The pinned `@openai/codex` 0.157.1 generated schema defines `thread/tokenUsage/updated` with required `threadId`, `turnId`, and `tokenUsage`; `tokenUsage` requires `total` and `last` and may include nullable `modelContextWindow`. Each breakdown requires integer `inputTokens`, `cachedInputTokens`, `outputTokens`, `reasoningOutputTokens`, and `totalTokens`; `cacheWriteInputTokens` is optional and defaults to zero. The bounded parser accepts only nonnegative safe integers and a positive safe context-window integer when present. Unknown fields are discarded. Unparseable snapshots with a correlatable active turn mark that turn degraded and are not stored; uncorrelatable notifications are ignored without failing a turn.

`total` is the cumulative thread snapshot; `last` is informational, may change several times, and is never added or used to derive a turn delta. Capture a new thread's zero baseline before its first turn and a continuation's last known cumulative total before issuing the next turn. Set `end_total` only when a terminal notification was observed and a valid snapshot arrived during that turn. Compute field-wise deltas only when start/end and every intervening cumulative snapshot are complete and monotonic. `authoritative_delta` requires those valid monotonic snapshots; `degraded` means telemetry exists but malformed/decreasing counters, a missing baseline, or recovery prevents a trustworthy delta; `unavailable` means no meaningful snapshot was observed. The task-level quality describes the latest turn's delta assessment. Missing snapshots leave `end_total`/delta null. On a decreasing cumulative snapshot, keep the last defensible `thread_total`, update independently valid `last`/context values, mark quality degraded, and do not produce a negative or clamped delta. `totalTokens` is authoritative; cached and reasoning counts are subsets and are not added again. No explicit model-request count exists, so persist null and never substitute notification count.

Persist the newest valid `last` breakdown; repeated values replace the prior snapshot and are never summed. Persist the latest valid context window per turn and task; missing or null values preserve the prior known value, while a changed positive value replaces it. Per-turn activity summaries have fixed categories for command execution, file change, MCP tool call, dynamic tool call, and other (including plan and unrecognized item types). They store only started/completed/failed counts plus duration sample count and total. Durations use matching item start/completion timestamps and are retained only when nonnegative and at most 24 hours. Raw item IDs are held in memory only to pair durations. `requestUserInput` wait duration remains in the existing input-wait fields and is not added to activity durations. The <=1,000-event timeline remains independently bounded, and fixed per-turn aggregates survive its truncation. Persist only sanitized timeline sequence/time/category/status/duration/turn values: never command text/output, reasoning, file content, MCP arguments/results, secrets, payloads, item IDs, or paths. No costs/dashboard.

## 12. Recovery and persistence

### M3A authorization and locking foundation

The M3A implementation removes both M1 blockers: policy and registry mutations share the global OS-backed lock, and each registration receives a random UUID independent of timestamps. Removing a project leaves its old policy entry stale. Re-adding the same ID/root creates a different UUID, so an old authorization cannot match even when timestamps are identical. Legacy v1 project records and policy entries without a UUID remain parseable but are not considered authorized; a user must explicitly re-enable through the local TTY.

Crash ordering is fail-safe: project removal atomically removes the registry record while holding the config lock; it need not mutate a second policy file. If the process stops after removal, the old policy is not registered. Re-add writes a new registration UUID, so the old policy remains stale. For a legacy record, explicit enable writes the new registration UUID to `projects.json` first, then writes authorization under a fresh config-lock transaction after re-reading the registry. A crash between those durable writes leaves the project unauthorized/stale. The complete cross-platform M3A gate passed in GitHub Actions run 36209781951 on Windows, Ubuntu, and macOS with Node 20 and 24, including real native multiprocess lock tests. Linux musl remains unsupported.

#### M4A — internal default-mode execution

M4A is an internal service only. It does not register MCP tools, add a CLI execution command, enable Plan mode or continuation, relay App Server requests, or collect usage/activity telemetry. `AgentExecutionAdapter` exposes only fixed thread start, fixed-policy turn start, turn interruption, normalized lifecycle events, and close. The start gate takes the configuration mutation lock, reloads and validates the registered Git project and enabled authorization against the current registration UUID, timestamp, and canonical-root fingerprint, resolves an explicitly allowed or configured default profile, checks request idempotency, reserves capacity, and attempts the project writer lock. The lock order is always CONFIG MUTATION then PROJECT WRITER. The configuration lock is released after the writer lease is held. Disable and project removal take the same order and return `project_busy` while an execution owns the writer lease. An identical request ID retry returns its allocation before another writer lease or capacity slot is acquired.

At most four turns can be active across distinct projects. Intent and request idempotency are persisted in `queued` before Git baseline capture. The path-free baseline stores branch, HEAD (null for an unborn repository), filtered change counts, and a truncation flag, and is persisted before any App Server startup, account, model, or thread request. `running` is persisted only after `turn/start` returns an accepted turn ID. A new `startTask` rejects with a sanitized cause if setup fails before acceptance; its allocated task remains durably `failed` (or `interrupted` if acceptance became uncertain), and its writer/capacity lease is released only after terminal persistence. If the `turn/start` request may have reached App Server but its response is lost or invalid, the session is closed and the task is settled `interrupted`. An identical request ID retry returns the original allocation and never starts another turn. Once acceptance is known and `startTask` returns, later model failure is normal asynchronous lifecycle state. Final output accepts only a completed `agentMessage` in `final_answer` phase and is UTF-8 bounded to 64 KiB. Raw protocol request IDs/parameters, command output, tool arguments, and other item payloads are not persisted. Every upstream server request receives a protocol error. A correlated request fails and interrupts its task; malformed or uncorrelated requests fail the App Server session and interrupt active tasks. No turn is automatically replayed after process death.

App Server requests explicitly set the one canonical runtime root, workspace-write mode, `approvalPolicy: "never"`, and the exact `workspaceWrite` turn policy with only that writable root, network disabled, and both temporary-directory exclusions enabled. #### M4B — public MCP façade (implemented and committed; six-job CI passed)

M4B registers exactly `task_start`, `task_get`, `tasks_list`, and `task_cancel` when stdio explicitly constructs the server with a lazy task host.
