# Context Bridge v0.3 implementation specification

**Status:** M0 roadmap/specification; implementation not started.

**Theme:** Productization and user experience centered on a local management GUI.

## Release goals and boundaries

- Add a local GUI for managing Context Bridge projects, profiles, and persisted activity.
- Keep existing MCP clients and public MCP behavior stable throughout v0.3.
- Keep the GUI as a local management surface; it is not a general-purpose agent client.
- Implement the GUI by calling typed internal services shared with existing application logic.
- Keep existing authorization, registration, and project safety rules authoritative.
- Avoid background services, remote dependencies, and network-facing management endpoints.

## Architecture

- Add the future `ctxbridge ui` command as the GUI entry point.
- Start a Node loopback server bound only to `127.0.0.1`.
- Select an ephemeral port by default and report the local URL to the launching process.
- Keep this server completely separate from the existing MCP HTTP transport.
- Do not route GUI requests through MCP or make the GUI call MCP back into itself.
- Serve a Vue 3, Vite, and TypeScript single-page application.
- Bundle frontend assets locally with the application.
- Do not use Nuxt, Electron, Tauri, or Rust for this release.
- Expose typed internal service interfaces for GUI operations.
- Reuse domain validation and authorization rules instead of duplicating CLI logic.
- Keep process startup, server shutdown, and UI errors understandable to the user.

## GUI security requirements

- Generate a cryptographically random authentication token for each server process.
- Bootstrap the token to the SPA through the URL fragment.
- Hold the token only in frontend memory and/or sessionStorage.
- Clear the fragment immediately after token bootstrap.
- Send the token in a custom authentication header on every API call.
- Reject unauthenticated API requests, including requests from local webpages.
- Validate the Host header against the exact active loopback host and port.
- Validate Origin against the exact allowed GUI origin; reject unexpected origins.
- Apply a strict Content-Security-Policy suitable for bundled local assets.
- Set `Referrer-Policy: no-referrer`.
- Do not enable wildcard CORS.
- Do not load scripts, styles, fonts, images, or other assets from remote origins.
- Avoid exposing the token in logs, error messages, or navigated links.
- Authenticated local GUI views may display absolute local paths when useful.
- Continue hiding absolute local paths from MCP responses.

## Pages and workflows

### Dashboard

- Summarize registered projects and their current availability.
- Show concise recent task, usage, and activity information when available.
- Link to relevant project details and settings.

### Projects and project detail

- List registered projects and show availability and Git status.
- Add a project using the existing registration and authorization rules.
- Remove a project with clear identification and confirmation.
- Show a project's enabled agent state and relevant configuration.
- Enable or disable the agent only after an explicit warning and confirmation.
- Present registration errors and unavailable paths without weakening path checks.

### Profiles and policy

- Create, read, update, and delete profiles using validated profile fields.
- Set the default profile.
- Configure each project's allowed profiles and default profile.
- Reuse current App Server capability validation for profile and policy choices.
- Explain invalid or unsupported selections before saving them.

### Tasks and usage

- Display bounded, read-only persisted task, turn, usage, and activity history.
- Provide useful filtering and pagination within explicit history bounds.
- Do not add an arbitrary prompt client to the GUI in v0.3.
- Do not claim or expose cross-process task cancellation unless its behavior is proven.
- Keep history views resilient to missing, partial, or concurrently updated records.

### Settings and diagnostics

- Show relevant local configuration and service diagnostics.
- Provide safe, actionable guidance for common startup and project problems.
- Do not display secrets or expand diagnostic output beyond existing privacy rules.

## Safe local branch management

- Offer branch management only in the GUI; never add it to MCP.
- List local branches and identify the current branch.
- Create a local branch from the current HEAD and switch to it.
- Switch to an existing local branch.
- Require a completely clean working tree before either branch mutation.
- Acquire the same per-project writer lock used by other project mutations.
- Revalidate project registration, canonical root, and worktree before mutation.
- Repeat registration, root, and worktree validation after mutation.
- Validate branch names against Git's branch-name rules before invoking Git.
- Invoke Git with fixed argument arrays and `shell=false`.
- Do not interpolate user-controlled values into shell command strings.
- Do not provide commit, push, pull, fetch, merge, rebase, reset, or clean operations.
- Do not provide force operations, branch deletion, remote operations, or detached HEAD.
- Do not accept arbitrary refs, initiate network access, or access credentials.
- Report a failed operation without attempting a broader recovery mutation.

## Public MCP invariant

- Preserve the stdio MCP surface at exactly 15 tools throughout v0.3.
- Preserve the HTTP MCP surface at exactly 9 read-only tools throughout v0.3.
- GUI-only management capabilities must not expand either MCP surface.
- Keep these counts and read-only HTTP behavior in release acceptance evidence.

## Risks and mitigations

- Loopback attacks: require a per-process token, exact Host/Origin validation, strict CSP, and no wildcard CORS.
- CLI/UI logic divergence: use typed shared internal services and shared validation.
- Branch/task races: use the project writer lock and revalidate project identity around mutations.
- Concurrent task-store reads: bound history reads and handle partial or changing records safely.
- Asset packaging failures: bundle local assets and verify fresh-install startup.
- Windows-first assumptions: record Windows acceptance and best-effort Linux/macOS findings separately.
- Accidental MCP expansion: assert public tool counts and HTTP read-only behavior at release gates.

## Deferred beyond v0.3

- Desktop wrapper, tray integration, and autostart.
- Git history views and remote Git mutations.
- GUI task authoring or arbitrary prompt submission.
- Automatic updates and network-based version checks.
- Daemon or cloud backend.
- Generic shell access.
- Support for other agent providers.
